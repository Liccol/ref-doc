# MiniMax Code 特性变更总结（2026-10-08 ～ 2026-10-14）

## 新特性与能力扩展

| 日期 | 特性 | 变化与使用边界 | 来源 |
| --- | --- | --- | --- |
| 10-08 | 启动级 system prompt 覆盖 | TUI、`exec`、`exec review` 和 `mcode acp` 新增 replace/append 的 inline/file 参数；文件在启动时读取，缺失、不可读或为空会直接失败。覆盖只驻留当前进程，不写入 Session/配置，也不传给 Task 子 Agent；Runtime rules、项目指令、Environment、Memory 和 Skills 仍按原方式组合 | [#444](https://github.com/MiniMax-AI/minimax-code/pull/444) |
| 10-13 | 终端程序状态协议 | 交互 TUI 通过 OSC 7501 报告 running、等待审批/输入/登录、完成和失败，支持的终端无需解析屏幕内容；仅 TTY 生效，不用于 headless exec / ACP，可用 `tui.programStatus: false` 关闭。登录后状态可恢复，真实终端展示未由上游手工验证 | [#471](https://github.com/MiniMax-AI/minimax-code/pull/471) |

## 问题修复与行为变化

### Agent、模型请求与任务状态

| 日期 | 主题 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- | --- |
| 10-08 | Ask / Plan 等待状态 | `ask_user` 已产生持久待回答请求却没有最终回复时，会被判为可重试的 `EMPTY_RESPONSE` → turn 结算为等待用户继续；只把 `questionnaire.ask` 视为新请求 | [#444](https://github.com/MiniMax-AI/minimax-code/pull/444) |
| 10-08 | 一次性定时任务 | `cron once --after 1w` 被拒绝，超长无效数字还可能拖慢解析 → 支持 `w` 周单位并限制解析工作量；`1w` 表示一周后执行一次，不表示每周重复，`1week` 仍不支持 | [#435](https://github.com/MiniMax-AI/minimax-code/pull/435) |
| 10-09 | 长时 exec timeout | Node 会把超过 `2,147,483,647 ms` 的 timer 压到约 1 ms，导致 `--timeout 600h` 几乎立即取消 → 将总时长拆成多个上限内 timer；上游用 fake timer 验证，没有实际等待多日 | [#448](https://github.com/MiniMax-AI/minimax-code/pull/448) |
| 10-09 | MiniMax API-key effort | `minimax_api` 路径会删除 `output_config`，使显式 `--effort` 未进入请求 → M3.1 Flash 的 low/high/xhigh/max 等显式值保留到 wire；`default`、普通开关式 thinking 模型和其他 provider 不变。上游截获请求体验证，未确认开放平台对全部档位的线上接受情况 | [#461](https://github.com/MiniMax-AI/minimax-code/pull/461) |
| 10-09 | 超限请求与压缩 | HTTP 413、本地 body 上限和明确 context overflow 原先会按瞬时错误重复发送 → 改为确定性拒绝，不再原样重试。较早合入的“一次强制压缩后重发”因重发没有重新执行截图限制和 session identity 等请求转换，于同日被移除；最终 main 只保留分类与停止重复重试 | [#460](https://github.com/MiniMax-AI/minimax-code/pull/460)、[#466](https://github.com/MiniMax-AI/minimax-code/pull/466) |
| 10-09 | 上下文提醒与 session ID | 预算/时间/session 提醒减少到必要时机；自动压缩若移除了历史中的 session ID，会追加隐藏 identity reminder，避免模型在下一轮前失去会话身份 | [#459](https://github.com/MiniMax-AI/minimax-code/pull/459)、[#466](https://github.com/MiniMax-AI/minimax-code/pull/466) |
| 10-11 | Codex OAuth 模型目录 | 模型发现请求的兼容 `client_version` 从 `0.153.0` 更新到 `0.162.0`，修复报告中的目录缺项；上游未执行真实 ChatGPT OAuth，也未独立验证账号侧新增模型是否可用 | [#477](https://github.com/MiniMax-AI/minimax-code/pull/477) |

### TUI、网络与安装

| 日期 | 主题 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- | --- |
| 10-08 | Scrollback 稳定性 | 无键盘输入时，历史行变化或周期 footer 刷新可能触发全量重建并把已上滚用户拉回顶部 → 保留已经进入历史的反馈 cell，并将剩余重建延迟到下一次输入、稳定 resize 或退出 | [#434](https://github.com/MiniMax-AI/minimax-code/pull/434) |
| 10-08 | 输出速率 | provider 在 turn 开头一次释放缓存内容会造成虚高 tok/s → 解码窗口不足请求时长 10% 且推算超过 1000 tok/s 的开头 burst 不纳入统计；持续高速输出仍计入 | [#454](https://github.com/MiniMax-AI/minimax-code/pull/454) |
| 10-09 | Homebrew Node 更新 | npm-prefix 更新把 launcher 固定到版本化 Cellar Node，`brew upgrade` 删除旧 keg 后 CLI 无法启动 → 优先复用 receipt 中仍可用的 Node，并将 Cellar receipt 迁到稳定路径；缺失时显示重新安装提示 | [#445](https://github.com/MiniMax-AI/minimax-code/pull/445) |
| 10-09 | SOCKS5 代理 | `ALL_PROXY=socks5://...` 会使 CLI 启动失败 → 支持 `socks5://`、`socks5h://`、`socks://`、认证及 IPv6 proxy，保留 `NO_PROXY` 直连；无效 `ALL_PROXY` 脱敏告警后忽略，显式错误的 `HTTP_PROXY` / `HTTPS_PROXY` 仍报错。Bedrock provider 路径仍不支持 SOCKS | [#465](https://github.com/MiniMax-AI/minimax-code/pull/465) |
