# 2026 年 10 月 22 日至 28 日 Tool Calling 变更记录

## 新特性与能力扩展

### Reasoning effort 映射

新增 `--reasoning-effort-map`，把客户端提交的 effort 显式改写为当前 chat template 支持的值，例如 `'{"minimal":"low","medium":"low","xhigh":"max"}'`。Python 前端覆盖 Chat Completions、Responses、Anthropic Messages、Harmony 和 render server；Rust 前端覆盖 chat/render/tokenize 及 Python 启动的 Rust frontend。未列出的值保持不变，`chat_template_kwargs.reasoning_effort` 作为直通入口不参与映射；未配置时无需调整存量启动命令。Python PR 只完成了单元与渲染验证，没有针对真实服务模型做端到端评测；Rust PR 使用 DeepSeek V4.1 render server 验证了 `medium → high`。[#61094](https://github.com/vllm-project/vllm/pull/61094)、[#62312](https://github.com/vllm-project/vllm/pull/62312)

### Kolibri 1 使用 HF response template parser

Kolibri 1 checkpoint 已提供 `response_template`，文档确认可用 `--tool-call-parser hf --reasoning-parser hf --enable-auto-tool-choice`，无需模型专用 parser；作者在 `Aleph-Alpha/Kolibri-1` FP8、TP=2 上验证了流式/非流式自动工具调用和 reasoning 开关。当前 HF parser 不能为该格式生成可保证 `required` 或命名调用的 structural grammar，因此这两类请求可能被拒绝或不能保证一定调用；原先使用 Hermes/Qwen3 parser 的命令不会自动切换。[#62885](https://github.com/vllm-project/vllm/pull/62885)

## 兼容性修复

| 日期 | 类型 | 变更与边界 | 来源 |
| --- | --- | --- | --- |
| 10-22 | structured-output 编译错误 | EngineCore 的 grammar 编译失败现在带 `validation_error`，Rust HTTP/SSE 返回 400、gRPC 返回 `INVALID_ARGUMENT`，不再表现为 500 或空 200；仅改变错误传递，不放宽 schema/grammar 能力 | [#62872](https://github.com/vllm-project/vllm/pull/62872) |
| 10-23 | Rust 空工具列表 | Rust Chat Completions 与 Python 对齐，`tools: []` 返回 400；应省略字段或提供至少一个工具，`tools: null` 仍可接受 | [#63060](https://github.com/vllm-project/vllm/pull/63060) |
| 10-23 | 历史工具调用空参数 | assistant 历史中的 `arguments: ""` 在 Rust 前端按 `{}` 渲染，避免 HF、DeepSeek 等 renderer 把空串当非法 JSON 返回 500；空白串和其他畸形 JSON 不会被自动修复 | [#63314](https://github.com/vllm-project/vllm/pull/63314) |
| 10-24 | LM Format Enforcer 弃用提示 | 选择 `lm-format-enforcer` structured-output backend 时新增一次性弃用警告和迁移指引；本期仅增加警告，backend、依赖和解码行为仍保留。PR 提出的移除目标是 v0.35.0，后续版本仍需另行确认 | [#63423](https://github.com/vllm-project/vllm/pull/63423) |
| 10-26 | Rust 统一 structured-output backend | Rust HTTP、gRPC 和 parser grammar 统一使用服务配置的 backend，默认/`auto` 为 xgrammar，消除首个请求决定引擎 backend 后导致严格、required、命名工具调用返回 500 的顺序依赖。使用 guidance/outlines/LMFE 时不会组合 xgrammar structural-tag parser grammar；`--tool-strict-level` 的 function 或 parameter 模式仅允许 xgrammar，存量非 xgrammar 启动命令需检查这一限制 | [#62456](https://github.com/vllm-project/vllm/pull/62456) |

## 模型 parser 与 grammar 重构

| 日期 | 类型 | 变更与用户可见行为 | 来源 |
| --- | --- | --- | --- |
| 10-23、10-27 | Rust Gemma 4 parser 兼容 | Rust parser 新增无 `call:` 前缀、括号参数和仅函数名三种 checkpoint 输出形式；name-only 调用返回空对象参数，括号与花括号必须成对。仅放宽解析，Gemma 4 仍没有新增输出 grammar | [#63059](https://github.com/vllm-project/vllm/pull/63059)、[#63768](https://github.com/vllm-project/vllm/pull/63768) |
| 10-26 | `llama3_json` 迁移 ParserEngine | `llama3_json` 的流式实现迁入统一 ParserEngine，减少 chunk 切分导致的无效 JSON 和 AST 错误；启动参数不变。新实现暂不流式发送 arguments 增量，参数会在可解析后集中返回，可能增加首个参数 delta 延迟 | [#63569](https://github.com/vllm-project/vllm/pull/63569) |
| 10-27 | spec decode grammar 状态 | grammar-invalid draft 不再在 rejection sampling 前被直接裁掉，而是保留给验证并在失败时原子回滚 grammar 状态，修复 structured outputs + speculative decode 的输出分布偏移；作者报告 async 路径约有小幅收益、sync 路径约有 2% 回退，结果来自其 H100 基准 | [#61557](https://github.com/vllm-project/vllm/pull/61557) |
| 10-27 | Rust Lark/EBNF 判定 | Rust frontend 改用与 Python 相同的 Lark 检测规则，注释里出现 `::=` 的 Lark grammar 不再被误当 EBNF 并组合进 structural tag。Lark 仍不能作为 parser-built structural-tag grammar 的叶子组合，只能走原生 grammar 字段 | [#63709](https://github.com/vllm-project/vllm/pull/63709) |

## 问题修复

### Tool parser 与流式调用

| 日期 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- |
| 10-22 | Kimi K3 Responses API 没有关闭 special-token 间空格，XTML marker 会泄漏到正文且字符串参数空格可能变化 → `ResponsesRequest` 增加并透传 `spaces_between_special_tokens`，Kimi K3 自动关闭它；Chat Completions 行为不变 | [#62507](https://github.com/vllm-project/vllm/pull/62507) |
| 10-23 | Responses 已接收并回显 `max_tool_calls`，但内置工具循环未执行限制 → 达到请求上限后停止继续执行 built-in tools；外部 function tool 的客户端执行循环不在此范围 | [#47112](https://github.com/vllm-project/vllm/pull/47112) |
| 10-23 | schema 类型为 `number` 时，大于 IEEE-754 精确范围的整数先转 float 会被改值 → 优先按整数解析，K2 Horizon 及共用 ParserEngine 的工具参数可保持原值；小数、指数和非有限值沿用原路径 | [#55743](https://github.com/vllm-project/vllm/pull/55743) |
| 10-24 | 流式 Chat/derender 没有统一执行 batch 的 `tool_choice` 过滤，gpt-oss 的 `none` 或任意 parser 的 `null` 仍可能返回工具调用 → 流式与非流式一致丢弃调用并返回 `finish_reason=stop`；`auto`、`required` 和命名调用不变 | [#63345](https://github.com/vllm-project/vllm/pull/63345) |
| 10-26 | Step3 参数值包含 `<`（SQL、HTML 等）时整项被静默丢弃 → 解析到对应结束标签，流式和非流式均保留值；字面 `</steptml:parameter>` 仍会提前结束，因为协议没有转义 | [#60968](https://github.com/vllm-project/vllm/pull/60968) |
| 10-26 | Jamba 在函数名 delta 同时带首段参数时，用“当前完整 JSON 与上次 JSON”求差会漏发开头 → 以已实际发送的参数长度为锚点补发，修复多 token chunk 下客户端累积出无效 JSON | [#55669](https://github.com/vllm-project/vllm/pull/55669) |

## vLLM Ascend 相关变更

本期 main 分支没有 Tool Calling 或 reasoning 的运行时变更。文档 PR [#19414](https://github.com/vllm-project/vllm-ascend/pull/19414) 仅澄清 GLM-5.3 在关闭 thinking 后仍可能生成 reasoning 文本：vLLM 放在 `content`，vLLM Ascend 放在 `reasoning`；该说明只适用于 GLM-5.3，运行行为未改变。
