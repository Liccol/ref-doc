# 2026 年 10 月 15 日至 21 日 Tool Calling 变更记录

## 新特性与能力扩展

### Beam 与新模型 parser

| 日期 | 特性 | 适用范围、原理与启用方式 | 来源 |
| --- | --- | --- | --- |
| 10-16 | Beam parser | 新增 `beam` reasoning/tool parser，按 checkpoint 的 `response_template` 解析和约束 channel/tool 输出；启动时使用 `--reasoning-parser beam --tool-call-parser beam`，自动工具调用仍需 `--enable-auto-tool-choice`。默认每个请求都启用 parser grammar；如需保留未约束输出，可设置 `VLLM_BEAM_ALWAYS_CONSTRAIN_OUTPUT=0`。parser 合入不等于任意 Beam 权重均已完成端到端支持 | [#62052](https://github.com/vllm-project/vllm/pull/62052) |
| 10-19 | Muse Spark Open parser | 新增 `muse`（别名 `musespark1x`）reasoning/tool parser，按 ATEM channel/recipient 协议把 reasoning、正文和工具调用拆开；可显式使用 `--enable-auto-tool-choice --tool-call-parser muse --reasoning-parser muse`。Rust 前端可按 Muse Spark 模型名自动选择，Python 启动命令仍应显式配置；本次只确认 parser 与文档，不能据此确认全部 checkpoint 可执行 | [#62207](https://github.com/vllm-project/vllm/pull/62207) |
| 10-19 | Step-5-Preview 支持 | 新增 Step-5 模型实现、`step5` tool parser 与 reasoning parser；工具协议沿用 Qwen3-Coder 风格并保留参数空白。Step-5 部署可使用 `--enable-auto-tool-choice --tool-call-parser step5 --reasoning-parser step5`；我不确定两套前端是否都会仅凭模型名自动选择，因此存量显式启动命令应补齐这两个 parser 参数 | [#61727](https://github.com/vllm-project/vllm/pull/61727) |
| 10-21 | Generate API 结构化反解析 | `/inference/v1/generate` 新增 `output_mode=derender`：提供 `parse_context` 后，可把输出还原为带 `content`、`reasoning_content` 和 `tool_calls` 的 assistant 消息；无效上下文返回 400，batch 在 `parallel_tool_calls=false` 时也按单调用约束。该能力复用现有 parser，不改变 OpenAI API 启动参数 | [#60082](https://github.com/vllm-project/vllm/pull/60082) |

## 兼容性修复

| 日期 | 类型 | 变更与边界 | 来源 |
| --- | --- | --- | --- |
| 10-15 | strict level 回退 | 未设置 `--tool-strict-level` 时，改为使用 parser 自身默认值，再回退到 `auto`；显式 `auto` 仍表示关闭 parser 默认强约束。GLM-4.7 的 Rust/Python 默认行为由此对齐，已有显式配置无需调整 | [#61328](https://github.com/vllm-project/vllm/pull/61328) |
| 10-18 | Rust gRPC structural tag | Rust gRPC structured outputs 改用 xgrammar，parser 生成的 structural-tag grammar 可正常执行工具约束；现有工具 parser 参数不变 | [#61892](https://github.com/vllm-project/vllm/pull/61892) |
| 10-20 | 请求级 chat template | Rust 前端补齐 `--trust-request-chat-template`，允许请求传入 chat template；依赖请求模板表达工具协议的客户端，只有显式开启后才会接受该字段 | [#62673](https://github.com/vllm-project/vllm/pull/62673) |
| 10-20 | structured-output 后端一致性 | 引擎首次建立后会固定 structured-output backend；后续请求若切换到另一 backend，改为返回 400，避免缓存 backend 与请求配置不一致后在执行期报 500 | [#49625](https://github.com/vllm-project/vllm/pull/49625) |
| 10-21 | Rust 约束优先级 | Rust 前端改为与 Python 一致：同时提供 `response_format` 和 `structured_outputs` 时由 `response_format` 生效；工具 parser 生成的约束仍按既有组合规则处理 | [#62823](https://github.com/vllm-project/vllm/pull/62823) |

## 模型 parser 与 grammar 重构

| 日期 | 类型 | 变更与用户可见行为 | 来源 |
| --- | --- | --- | --- |
| 10-16 | MiniMax M2 增量参数解析 | 长字符串工具参数不再每个 chunk 重解析全部累计 JSON；作者基准中 16 KiB 参数由约 5.9 s 降至 26 ms，输出格式不变，使用 MiniMax M2 parser 的启动命令无需调整 | [#62035](https://github.com/vllm-project/vllm/pull/62035) |
| 10-17 | Qwen3 系 parser 增量参数解析 | Qwen3-Coder/XML 共用的字符串参数改为线性增量发送；影响 `qwen3_coder`、`qwen3_xml` 及复用该实现的 Seed-OSS、Step3p5、Nemotron-v3、Granite thinking、MiniCPM-V 等 parser。作者基准中 12 KiB 参数由约 2.1 s 降至 11 ms，参数与启动方式不变 | [#62027](https://github.com/vllm-project/vllm/pull/62027) |
| 10-18 | speculative decode grammar mask | structured-output grammar 的 token mask 改为按 spec decode 展开后的真实 token 位置映射，避免草稿 token 接受/拒绝后约束错位；上游完成单元测试，GPU 端到端测试在 PR 中标为待补 | [#52477](https://github.com/vllm-project/vllm/pull/52477) |
| 10-20 | Rust grammar 深度上限 | Rust 请求入口对 JSON schema 与 parser 生成的 structural tags 增加深度限制（JSON 64 层、structural tags 80 层），超限在进入引擎前返回 400，避免递归 grammar 消耗失控 | [#62661](https://github.com/vllm-project/vllm/pull/62661) |

## 问题修复

### Tool parser 与响应状态

| 日期 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- |
| 10-15 | `tool_choice=required` 最终未解析出调用时仍返回 `finish_reason=tool_calls`；自动调用被 `max_tokens` 截断时也会误报完成 → Chat Completions 按实际解析结果返回 finish reason，Responses 的 item 与终止事件在截断时标为 incomplete | [#59324](https://github.com/vllm-project/vllm/pull/59324) |
| 10-16 | batch derender 会重新生成工具调用 ID，无法与 parser 原始 ID 对齐 → 保留 parser 产生的 ID，包括 `functions.<name>:<index>` 形式 | [#61852](https://github.com/vllm-project/vllm/pull/61852) |
| 10-19 | 非流式 parser 在一个工具调用之后丢弃继续生成的正文 → 与流式路径一致保留调用后的文本 | [#56270](https://github.com/vllm-project/vllm/pull/56270) |
| 10-19 | DeepSeek V3/V3.1 Python parser 只接受单行 JSON，pretty-printed 多行参数无法解析 → 正则跨行匹配并恢复结构化工具参数；Rust 实现原本已能处理该形式。上游用 parser 测试验证，未报告真实多 GPU 服务验证 | [#60362](https://github.com/vllm-project/vllm/pull/60362) |

### Reasoning 与工具 grammar

| 日期 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- |
| 10-16 | GLM 等模型用工具起始 token 隐式结束 reasoning 时，reasoning parser 会先消费该 token，grammar 看不到状态转换 → 将隐式结束 token 同步送入 grammar mask，避免重复或丢失工具起始标记 | [#61574](https://github.com/vllm-project/vllm/pull/61574) |
| 10-16 | prompt 已闭合 reasoning block、并使用 `continue_final_message` 时，非流式路径仍按未结束 reasoning 解析，token 计数也可能落入错误字段 → 初始化时识别已闭合状态，正文与 reasoning 计数按真实 channel 归类；legacy parser 不受影响 | [#61857](https://github.com/vllm-project/vllm/pull/61857) |
