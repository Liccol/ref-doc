# 2026 年 10 月 8 日至 14 日 Tool Calling 变更记录

## 新特性与能力扩展

### Responses API 支持 Custom Tool Call

非 Harmony 的 `/v1/responses` 新增 `type=custom` 工具支持：服务端将自定义工具临时映射为单字符串 `input` 的函数形式，统一交给现有 parser、命名 `tool_choice` 和 structural-tag grammar 处理；流式响应使用 `response.custom_tool_call_input.delta` / `.done`，多轮输入中的 `custom_tool_call` 与 `custom_tool_call_output` 也可往返编码。

适用范围是非 Harmony Responses 路径，仍要求所选模型、chat template 和 tool parser 能生成并识别对应工具协议。沿用已有 `--enable-auto-tool-choice --tool-call-parser ...` 启动方式，不需要新增启动参数；该变更不会让原本不支持工具调用的模型自动获得该能力。[#57322](https://github.com/vllm-project/vllm/pull/57322)

## 兼容性修复

| 日期 | 类型 | 变更与边界 | 来源 |
| --- | --- | --- | --- |
| 10-08 | Batch Chat reasoning 透传 | `/v1/chat/completions/batch` 现在与单请求路径一样向引擎传递 `reasoning_ended` 和模板参数，避免关闭 thinking 后 grammar 仍等待推理结束、导致约束未启用 | [#59263](https://github.com/vllm-project/vllm/pull/59263) |
| 10-09 | Rust gRPC reasoning 控制 | `Generate` / `GenerateStream` 增加 reasoning gate、有效 chat-template 参数和 thinking token budget 的透传；依赖这些字段的客户端需要更新后的服务端，旧服务端会忽略新增字段 | [#59836](https://github.com/vllm-project/vllm/pull/59836) |
| 10-13 | Structural tag 后端校验 | `outlines` 和 `lm-format-enforcer` 不支持 structural tag 时，改为请求阶段返回 400，避免工具 parser 内部生成该约束后在引擎中以 `FINISHED_ERROR` 结束；需要 structural tag 的调用应使用支持它的后端 | [#58862](https://github.com/vllm-project/vllm/pull/58862) |
| 10-14 | 禁用 reasoning parser | Python 入口接受大小写不敏感的 `--reasoning-parser none`，将其视为未设置，并与 Rust 前端语义对齐；已有有效 parser 名称不变 | [#61525](https://github.com/vllm-project/vllm/pull/61525) |

## 问题修复

### Tool parser 与流式调用

| 日期 | 问题 → 修复后行为 | 来源 |
| --- | --- | --- |
| 10-08 | Responses 命名调用中，普通函数名可能遮蔽 namespace 内的短名称，且包含 `__` 的 namespace 子函数无法按完整本地名选择 → 仅为 namespace 工具注册短别名，并按精确 namespace 前缀解析；默认 Hermes structural-tag 路径的其他 namespace 限制不在本次范围 | [#59723](https://github.com/vllm-project/vllm/pull/59723) |
| 10-08 | `tool_choice=required` 的一个流式 delta 同时完成多个调用时，只发送部分调用或混淆 index/name/arguments → 对 Chat Completions、Responses 和 Anthropic Messages 逐个发出完整调用 | [#60354](https://github.com/vllm-project/vllm/pull/60354) |
| 10-09 | InternLM2 流式 JSON 字符串跨 chunk 时可能丢失引号和末尾大括号 → 按已发送文本计算增量，流式参数恢复为有效 JSON；数字文本被重新序列化产生的差异仍未处理 | [#60709](https://github.com/vllm-project/vllm/pull/60709) |
| 10-09 | LongCat 继承 Hermes structural tag，严格/命名调用生成 `<tool_call>`，但 LongCat parser 只识别自身标签 → 注册 `<longcat_tool_call>` grammar，使 `--tool-call-parser longcat` 的强制调用返回结构化 `tool_calls` | [#60747](https://github.com/vllm-project/vllm/pull/60747) |
| 10-12 | GLM-4.7/5.x 流式长字符串参数每个 chunk 都重解析全部已生成内容，CPU 开销随参数长度呈二次增长 → 增量扩展当前参数值，输出内容不变 | [#61253](https://github.com/vllm-project/vllm/pull/61253) |
| 10-13 | schema 声明 `integer` 时，模型输出整值浮点字符串（如 `"3.0"`）仍传给工具为字符串 → 转为整数 `3`；`3.5`、`NaN`、`inf` 仍不作整数转换 | [#61297](https://github.com/vllm-project/vllm/pull/61297) |
| 10-14 | Qwen3 在正文或 reasoning 中写出未闭合的 `<function=` 后，后续真实工具调用会被吞入错误片段 → 流式和非流式 parser 均可恢复后续调用，同时保留参数值中的字面 `<tool_call>` | [#59928](https://github.com/vllm-project/vllm/pull/59928) |
| 10-14 | Gemma4 字符串工具参数要等结束分隔符到达才整段发送，且长参数重复解析 → 改为逐 token、线性时间发送；上游使用 parser 测试验证，未做真实模型评测 | [#61494](https://github.com/vllm-project/vllm/pull/61494) |
